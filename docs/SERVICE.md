# SERVICE.md — Legacy2Next 서비스 기획

## 1. 배경 / 문제

- 레거시 현대화 과제를 시작하면 화면 분석 → 공통 컴포넌트 설계 → 목업/POC 제작을 사람이 직접 한다. 보통 1~2주가 걸린다
- 그동안 고객은 "바뀐 모습"을 볼 수 없어서, 방향을 정하거나 합의하는 일이 늦어진다

## 2. 사용 장면

- 소규모 AX 과제에서 고객·IT 담당자에게 레거시를 React로 바꾼 결과를 **하루 만에** 보여주는 용도
- 대상 사이트는 특정하지 않는다. 어떤 레거시 웹 시스템이든 URL로 받는다

## 3. 입력 / 출력

- **입력**: 레거시 웹 시스템 URL만 받는다. 소스 코드와 화면정의서는 받지 않는다
- **출력**: 아래 순서로 만든 `next-pjt/<별칭>/` 결과물
  1. 레거시 화면 분석
  2. Stitch로 TOBE 화면 디자인 생성
  3. 사용자 확인
  4. 공통 컴포넌트 생성
  5. 컴포넌트로 전체 화면 구현
  6. 빌드 검증 (실행 가능한 React 프로젝트인지 확인)

## 4. 핵심 기능 / 범위

### 하는 것
- **로그인 지원**: 로그인이 필요한 레거시도 대상이다
  - ID/PW 로그인: 계정은 사용자가 `.env`에 넣고, 에이전트는 거기서만 읽는다
  - 공인인증·간편인증 등 사람이 해야 하는 인증: 에이전트가 멈추고(`interrupt()`) 사용자가 화면에 띄운 브라우저에서 직접 인증한다. 인증이 끝나면 로그인 세션(Playwright `storageState`)을 저장해 이후 탐색에 재사용하고, 만료되면 다시 요청한다
  - 보안 프로그램 설치가 필요해 자동화 브라우저로 인증이 안 되는 사이트는, 사용자가 이미 로그인한 Chrome에 붙는 방식(Playwright MCP `--extension`)을 쓴다
- **Happy Path 우선 생성**: 에이전트가 핵심 유스케이스 흐름(Happy Path) **2~3개**를 골라 그 화면만 먼저 만든다. 후보를 실제로 처음부터 끝까지 걸어 보고, 끝까지 간(완주한) 흐름만 Happy Path로 고른다 (5절 Explorer)
- **테스트 데이터 없음 대응**: 조회 결과가 비어 있어도 진행한다. 조건을 넓혀 다시 조회 → 화면·응답에서 데이터 구조 추론 → 합성 데이터 생성 순으로 처리하고, 화면마다 데이터 출처(`observed`/`inferred`/`synthetic`)를 표시한다
- **ASIS와 비슷한 디자인**: TOBE 디자인은 ASIS의 레이아웃 골격(영역 배치, 메뉴 방식, 필드·컬럼 순서)과 브랜드 색을 이어받고 외형만 현대화한다. 변경 정도는 `conservative`(기본) / `balanced` / `bold` 중에서 고른다
- **재활용 가능한 수집 데이터**: 수집 원본과 분석 파생 데이터를 버전이 있는 구조로 저장해, 다시 크롤링하지 않고 재분석·디자인·질의에 쓴다 (5절 "수집 데이터 구조")
- **점진 확장**: 이후 요청마다 화면·흐름을 같은 프로젝트에 이어 붙여, 결국 전체 화면까지 만들 수 있게 한다. 이미 만든 공통 컴포넌트와 디자인을 재사용한다
- **데이터 연결 방식 제안**: 생성 앱이 레거시 백엔드를 직접 부를지, 목업 데이터로 동작할지 에이전트가 상황을 보고 판단한다. 근거와 함께 제안하고, 사용자가 승인한 방식으로 생성한다
- **변이 통일**: 레거시에서 비슷하지만 조금씩 다른 UI를 분석해 하나의 공통 컴포넌트로 묶을지, 변형(prop)으로 남길지 판단한다

### 하지 않는 것 (범위 밖)
- 백엔드 전환
- 배포
- TOBE 앱의 인증 연동 (레거시 탐색을 위한 로그인은 범위 안)
- 인증서 파일·인증 비밀번호를 에이전트가 직접 다루는 인증 자동화

## 5. 에이전트 구성

LangGraph **고정 그래프**로 구성한다. 단계 순서가 정해져 있으므로 LLM이 다음 단계를 고르는 Supervisor는 두지 않는다. LLM 판단으로 분기하는 곳은 맨 앞 Router 하나뿐이다.

```
/query ──▶ Router (의도: 신규 생성 / 확장 / 질의)
              │
              ▼
  ① Explorer  ── 로그인(.env 또는 ⏸ 사용자 인증) → Map → Hypothesize → Walk (Playwright MCP)
  ② Analyst   ── 사이트 성격 추론 → 화면 목록, 변이 통일 판단, Happy Path 후보, 데이터 연결 방식 제안
              ⏸ 승인 1: 분석 리뷰
  ③ Designer  ── Stitch: 디자인 시스템 먼저, 그다음 화면
              ⏸ 승인 2: 디자인 확인
  ④ Builder   ── Stitch HTML → 공통 컴포넌트 → 화면
  ⑤ Verifier  ── 빌드, Playwright 흐름 검증 → 실패하면 ④로 (재시도 횟수 제한)
              │
              ▼
  next-pjt/<별칭>/ + manifest
```

### 단계별 역할

- **Router**: `/query` 요청의 의도를 신규 생성 / 확장 / 질의로 나눈다
- **Explorer**: Playwright MCP로 로그인한 뒤 "넓게 지도 → 좁게 가설 → 실제로 걸어서 검증" 3단계로 수집한다
  1. **로그인**: 로그인 화면 유형을 판별한다 (ID/PW, 공인인증, 간편인증). ID/PW면 `.env` 값을 코드가 입력하고, 그 외에는 멈추고 사용자에게 인증을 넘긴다 (4절 로그인 지원)
  2. **Map**: 메뉴 트리·링크·폼·화면을 넓게 수집해 사이트맵(화면 노드 + 이동 엣지)을 만든다. 조회만 하고, 화면마다 LLM을 부르지 않는다
  3. **Hypothesize**: 사이트맵으로 사이트 성격을 1차 추론하고 유스케이스 후보 5~7개를 점수와 함께 뽑는다. 점수 기준은 메뉴에서 눈에 띄는 정도(상단 메뉴·대시보드 바로가기), 업무 완결성(조회→상세, 입력→확인→완료), 도메인 상식, 화면 재사용도
  4. **Walk**: 점수가 높은 후보부터 실제로 처음부터 끝까지 걸어 보며 Flow Trace(단계별 화면·동작·대상 요소·입력 종류·결과 화면·네트워크 호출)를 기록한다. 완주한 흐름이 2~3개 모이면 멈춘다. 완주하지 못한 후보는 이유(데이터 없음, 인증 필요, 쓰기 동작 미승인 등)를 남긴다
  - 빈 조회 결과를 만나면 "테스트 데이터 없음 대응" 순서(4절)로 처리한다. 등록 흐름을 실행해 데이터를 만드는 것은 쓰기 동작이므로 G1 승인을 받는다
  - 한 번 걸은 흐름은 재실행 스크립트(selector 기반)로 저장한다. 다시 수집하거나 확장할 때는 LLM 없이 재실행한다
- **Analyst**: 아래 순서로 분석한다
  1. **사이트 성격 추론**(가장 먼저): 수집한 데이터를 근거로 이 사이트가 무엇을 하는 시스템인지 추론한다 — 업무 도메인, 주요 사용자, 핵심 업무. 이후 모든 판단(Happy Path, 변이 통일, 데이터 방식, 디자인 톤)의 기준이 된다
  2. 화면 목록 정리
  3. 변이 통일 판단: 비슷한 UI를 하나의 공통 컴포넌트로 묶을지, 변형(prop)으로 남길지
  4. Happy Path 확정안: Explorer가 완주한 흐름 중 2~3개를 사이트 성격 기준으로 고르고, 고른 이유와 제외한 후보의 이유를 적는다
  5. 데이터 연결 방식 제안: 레거시 백엔드 호출 vs 목업, 근거 포함. 화면별 데이터 출처(`observed`/`inferred`/`synthetic`)를 함께 보여준다
  6. ASIS 디자인 추출: 화면별 레이아웃 골격과 사이트 전체의 브랜드 토큰(주색·폰트·간격)을 정리해 Designer에 넘긴다
- **Designer**: Stitch MCP로 디자인 시스템을 먼저 만들고, 그 시스템으로 Happy Path 화면 디자인을 만든다. 결과는 `next-pjt/<별칭>/design/`에 저장
  - 디자인 시스템은 ASIS 브랜드 토큰을 바탕으로 만든다
  - 화면 디자인 요청에는 ASIS 레이아웃 골격, 마스킹된 ASIS 스크린샷(참고 이미지), 변경 정도 설정을 함께 넘긴다
  - 화면마다 ASIS와 TOBE의 유사도 점수(영역 배치 겹침 정도 + 필드·컬럼 순서 일치율)를 계산한다. 이 점수로 "레이아웃 대폭 변경" 여부를 판정한다
- **Builder**: Stitch 디자인을 기준으로 공통 컴포넌트를 먼저 만들고, 그 컴포넌트로 화면을 구현한다. 승인된 데이터 방식으로 데이터 계층을 만든다
- **Verifier**: 빌드와 Happy Path 흐름 테스트를 돌린다. 실패하면 오류를 Builder에 돌려보내고, 정해진 횟수를 넘기면 멈추고 사용자에게 보고한다

### 사용자 승인 지점 (2곳)

1. **분석 리뷰** (② 이후): 사이트 성격 추론, Happy Path, 데이터 연결 방식, 변이 통일 결과를 한 번에 확인·수정한다
   - Happy Path마다 Flow Trace와 화면별 데이터 출처를 보여준다. 완주하지 못한 후보도 이유와 함께 보여주어, 사용자가 Happy Path를 바꿀 수 있게 한다
   - 디자인 변경 정도(`conservative`/`balanced`/`bold`)도 여기서 정한다
2. **디자인 확인** (③ 이후): Stitch 디자인을 확인한다. 승인 전에는 코드를 만들지 않는다
   - **레이아웃 대폭 변경 화면은 개별 승인**: ASIS 대비 레이아웃이 크게 바뀐 화면은 ASIS·TOBE 스크린샷을 나란히 보여주고 바뀐 점과 그렇게 바꾼 이유를 적어, 화면별로 따로 승인받는다 (일괄 승인에 포함하지 않는다)
   - **바뀐 점마다 이유**: 모든 화면(대폭 변경이 아닌 화면 포함)에서 바뀐 점마다 왜 그렇게 바꾸는지 적는다. 이유는 사이트 성격, 분석 리뷰에서 승인한 결정(변이 통일 등), ASIS의 사용성 문제에서 근거를 댄다
   - "크게 바뀜"의 예: 영역 배치 변경(메뉴·사이드바·본문 위치), 화면 분할·병합, 입력 필드 순서·그룹 재구성. 판정은 유사도 점수가 설정 기준값보다 낮은지로 한다

승인 지점 외에, 실행 중 필요할 때 멈추는 곳이 둘 있다: **사용자 인증 넘김**(로그인·세션 만료)과 **쓰기·위험 동작 승인**(G1).

### 수집 데이터 구조

원칙: **원본은 한 번 수집하고, 파생 데이터는 여러 번 만든다.** 다시 크롤링하지 않고도 재분석할 수 있게 한다. 모든 파일 구조는 Pydantic 모델로 정의하고 스키마 버전을 붙인다. 원본은 G5 마스킹을 거친 뒤에만 저장한다.

```
next-pjt/<별칭>/crawl/
  manifest.json            # 스키마 버전, 수집 시각, 화면·흐름 목록
  graph.json               # 사이트맵: 화면 노드 + 동작 엣지
  screens/<screen_id>/
    raw/                   # 마스킹본만 저장
      screenshot.png, aria.yml, dom.min.html, network.json, console.log
    derived/
      layout.json          # 영역 bbox(header/메뉴/본문/footer), 밀도, 그리드
      components.json      # 표(컬럼), 폼(라벨·타입·필수·검증), 버튼, 탭, 페이징
      data_schema.json     # 응답·표 헤더·폼에서 뽑은 필드 구조 + 데이터 출처
      tokens.json          # 화면에 실제 적용된 색·폰트·간격
  flows/<flow_id>.json     # Flow Trace + 재실행 스크립트 + 완주 여부·이유
  fixtures/                # 합성 데이터 (synthetic 표시)
```

- `derived/`는 Analyst·Designer 입력, Chroma 인덱스(질의), Verifier 기능 보존 대조에 함께 쓴다
- `fixtures/`는 목업 데이터 방식일 때 TOBE의 MSW(Mock Service Worker) 핸들러 데이터로 쓴다

### 점진 확장

- `next-pjt/<별칭>/`에 manifest를 두고 만든 화면·공통 컴포넌트·승인된 결정을 기록한다
- 확장 요청이 오면 manifest를 읽고 ②부터 다시 돌되, 아직 만들지 않은 화면만 대상으로 한다. 이미 만든 컴포넌트와 디자인은 재사용한다

## 6. 콘솔 UI (`ui/`)

에이전트에 요청을 보내고 진행 상황·결과를 확인하는 화면. 화면 디자인은 Stitch로 먼저 만들고 확인받은 뒤 구현한다.

| 화면 | 내용 |
|---|---|
| 요청 입력 | 레거시 URL, 별칭 입력. 신규 생성 / 확장 요청 |
| 진행 상황 | 단계(①~⑤)별 상태와 로그를 **SSE로 실시간** 표시. 사용자 인증이 필요하면 "브라우저에서 인증을 완료해 주세요" 상태 카드를 띄우고, 완료 확인 후 이어서 진행 |
| 승인 | 분석 리뷰(사이트 성격·Happy Path와 Flow Trace·완주하지 못한 후보와 이유·화면별 데이터 출처·데이터 방식·변이 통일·디자인 변경 정도), 디자인 확인. 승인·수정·반려 |
| 결과 | 생성된 POC 실행 링크, manifest(만든 화면·컴포넌트·결정) |
| 질의 | 분석된 사이트에 대해 채팅으로 묻고 답한다 (Router의 "질의" 의도) |

## 7. 가드레일 요약

에이전트 실행 중에 지키는 규칙이다. 상세는 `docs/GUARDRAILS.md`.

- **쓰기·위험 동작은 승인 후**: 레거시 화면 수집은 조회 위주로 한다. 등록·수정·삭제·제출처럼 데이터를 바꾸는 동작과 로그아웃·비밀번호 변경·관리자 메뉴 진입은 실행 전에 멈추고(`interrupt()`) 사용자가 승인한 경우에만 실행한다
- **요청 URL 범위만 탐색**: 요청한 URL의 origin 밖으로는 이동하지 않는다. 다른 도메인의 SSO 로그인처럼 꼭 필요한 origin은 사용자가 설정 파일에 명시한 경우만 허용한다. Playwright MCP의 `--allowed-origins`는 보안 경계가 아니고 리다이렉트도 막지 않으므로, 에이전트 쪽에서 이동 전·후 URL을 다시 검사한다
- **계정 마스킹**: `.env` 계정 값은 로그·LLM 프롬프트·생성 결과물에 남기지 않는다. Playwright MCP의 `--secrets` 옵션으로 도구 응답에서 계정 값을 가린다
- **서비스 범위 밖 요청 거절**: `/query`에서 이 서비스와 상관없는 요청(잡담, 다른 작업 지시)은 Router가 거절한다
- **개인정보 마스킹**: 수집한 화면 데이터는 LLM·Stitch(외부 서비스)에 넘기기 전과 디스크에 저장하기 전에 Presidio로 개인정보(이름·전화번호·계좌번호 등)를 가린다. 한국어 형식은 정규식 인식기를 추가한다
- **화면 내용은 데이터로만 취급**: 수집한 페이지 텍스트는 프롬프트에서 지시와 분리된 데이터 영역에 넣는다. 페이지 안의 문구가 에이전트 지시처럼 보여도 따르지 않는다
- **생성 코드 의존성 제한**: Builder는 고정 템플릿에 있는 npm 패키지만 쓴다. 새 패키지가 필요하면 사용자 승인을 받는다
- **생성 범위 제한**: 에이전트가 쓰는 파일은 `next-pjt/<별칭>/` 안으로만 한정한다
- **실행 비용 한도**: 한 번 실행당 LLM 호출 수와 Verifier 재시도 횟수에 상한을 두고, 넘으면 멈추고 보고한다
- **로그인 세션 보호**: 저장한 로그인 세션 파일은 비밀값처럼 다룬다. git·로그·LLM·생성 결과물에 넣지 않고, 실행이 끝나면 삭제 여부를 묻는다. 인증서 파일과 인증 비밀번호는 에이전트가 다루지 않는다
- **합성 데이터 표시**: 에이전트가 만든 데이터는 `synthetic`으로 표시해 실제로 관찰한 데이터와 섞이지 않게 한다

## 8. 평가 기준

상세 평가셋과 결과는 `docs/EVAL.md`. 평가셋은 사용자가 직접 작성한다.

| 영역 | 평가 항목 |
|---|---|
| Explorer | Happy Path 화면을 빠짐없이 수집했는가, 고른 흐름을 끝까지 완주했는가 |
| Analyst | 사이트 성격 추론이 맞는가, Happy Path가 타당한가, 변이 통일 판단이 맞는가 |
| 기능 보존 | 레거시 Happy Path 화면의 입력 필드·버튼·조회 항목이 TOBE 화면에 빠짐없이 있는가 (수집한 화면 요소 ↔ 생성 화면 `data-testid` 대조) |
| Builder / Verifier | 빌드 성공, Happy Path 흐름 테스트 통과 |
| Router | 의도 분류 정확도, 범위 밖 요청 거절 |
| 가드레일 | 쓰기·위험 동작이 승인 없이 실행되지 않음, 계정·개인정보 노출 0건 |
| 소요 시간 | URL 입력부터 POC 완성까지 **엔드투엔드** 시간. 승인 대기를 포함한 전체 시간을 기준으로 하고, 에이전트 처리 시간과 승인 대기 시간을 따로 기록한다 |

**목표**: 가드레일 100%, 나머지 영역 80% 이상. 소요 시간은 엔드투엔드 1일 이내.
